Working
With Agents

A field guide to using AI well in a software development lifecycle — for engineers, QA, and product. Every rule here traces to a primary source from a frontier lab, a controlled study, or a practitioner whose work you can check, and every citation is stamped with the year it was published. Nothing in here is opinion dressed as evidence. Where the research disagrees, we say so.

Two things to know before you read. First: the practices are date-stamped, because coding-agent capability stepped up discontinuously around late 2025 and guidance written before that was authored against a weaker tool. Second: this was written for a team working in PCI scope, so several rules that read as best practice elsewhere are non-negotiable there — a useful lens even if you are not.

The one finding to internalise

Models produce code that runs at a 95% rate and code that is secure at 55% — and the security number has not improved in two years, nor does it improve with model size. The thing your eye checks (does it work?) is orthogonal to the thing that bites you.

Practical translation for a payments team: treat agent-generated code as untrusted input to your pipeline. SAST on every agent-authored PR, not a sample. Extra scrutiny on output encoding, logging, and Java specifically. No "the model is smarter now" exemptions.

07

Where the experts genuinely disagree

Two live disagreements you should know about, so nobody on this team cites one side as settled.

Should we tell agents to write tests first?

Yes — it fits the failure mode

Willison calls red/green TDD a "fantastic fit for coding agents," because the biggest risk with an agent is that it writes code that doesn't work, and every good model understands the shorthand. Kent Beck called TDD a superpower with agents precisely because agents introduce regressions.

Red/green TDD — Willison, Mar 2026 Augmented Coding — Beck, Jun 2025

Not as a mandated process

Böckeler ran the experiment — three task sizes, judged solution pairs — and found "no clearly discernable difference," with non-TDD runs sometimes scoring higher on design and test quality, at 3× the tokens. Her mechanism: test-first instructions work against the up-front design step agents benefit from. She's stopped mandating it and recommends mutation testing and static-analysis-triggered refactoring instead.

TDD inside the agent loop — Böckeler, Aug 2026

Where we land

Nobody disagrees that tests must exist and must be executed. The disagreement is narrowly about prescribing red-green-refactor as the agent's internal process. Böckeler's is the later evidence and the only experimental evidence, so: we mandate the outcome, not the process. Tests exist, tests run, test files are read-only to the implementing agent, and the writer is not the grader. How you get there is your call.

One thing to know before you cite this as a debate: as of late Aug 2026 nobody on the pro-TDD side has publicly answered Böckeler's result. Willison has not revised the chapter; Beck's nearest 2026 artifact is an exploratory piece on enforcing test-commit-revert inside the agent loop (Apr 2026) that predates her memo and reaches no verdict. This is an open question with one experiment on the table, not a settled argument.

How much autonomy?

Maximum, with the sandbox as the only control

Willison: "I run in YOLO mode all the time" — and in the same breath, "the only solution that's credible is to run coding agents in a sandbox," ideally on someone else's computer. Ronacher disables permission checks entirely, contained by Docker. The value is real and so is the containment requirement.

Living dangerously with Claude — Willison, Oct 2025 Agentic Coding Recommendations — Ronacher, Jun 2025

High on execution, zero at the merge boundary

Hashimoto: "I'm not shipping code I don't understand," and "please don't ever ship AI-written code without a thorough manual review." Note that Willison's own anti-patterns chapter says the same thing — the resolution is that autonomy governs execution inside a sandbox, never review before merge. That is the most commonly misread point in this literature.

Vibing a Non-Trivial Feature — Hashimoto, Oct 2025 Anti-patterns — Willison, Mar 2026

Where we land — and this one isn't negotiable

Full execution autonomy is fine inside a sandbox with no path to production credentials and default-deny egress. It is prohibited on any host that can reach the CDE, on any host holding CDE credentials, and in CI. Permission-bypass flags are a documented attacker primitive, not just a footgun — the s1ngularity npm compromise invoked developers' own AI CLIs with exactly those flags to steal 1,000+ tokens and ~20,000 files.

And zero autonomy at the merge boundary, always. PCI DSS 6.2.3 requires custom software to be reviewed before release; 6.2.3.1 adds a non-author reviewer and management approval where that review is manual, and 6.2.3 does permit automated review tools. The policy this guide recommends goes further: a human other than the requesting engineer reviews every agent-authored diff, with AI review as an additional pass rather than the one that counts.

Source freshness review — 21 Aug 2026, corrections 4 Sep 2026

Every pre-2026 source was re-checked against its current successor. Most held; six did not, and the guide above reflects the corrections rather than the originals:

  • OpenAI's GPT-5.2 prompting guide was superseded twice (GPT-5.5 in Apr 2026, GPT-5.6 in Jul 2026) and moved out of the Cookbook. Three practices it endorsed are simply absent from the current text, and the "ask 1–3 clarifying questions" rule became conditional. The headline change: don't port old prompts, start from the smallest one that preserves the contract.
  • Anthropic reversed its long-running-harness guidance in Mar 2026 — the one-feature-per-session structure was removed because current models decompose natively. Scaffolding is now something you strip as models improve.
  • "Multi-agent is a poor fit for most coding work" no longer holds. Anthropic shipped agent teams and published a parallel-agent compiler build. The cost caveat survives; the prohibition doesn't.
  • The AGENTS.md study's numbers were materially wrong in v1. The Jun 2026 revision finds no statistically significant benefit in either direction (+2.4%, p=0.21) against a highly significant ~20% cost penalty.
  • Package-hallucination rates dropped roughly fourfold on the 2026 model cohort — 4.6–6.1% against a 19.7% baseline. Real improvement; still not zero.
  • Veracode published a newer edition in Jul 2026: security pass rate 56%, up one point in two years.

Independent fact-check, 4 Sep 2026. A separate reviewer with no access to the drafting context re-opened the cited sources and found six defects, all corrected above: PCI DSS 6.2.3.1 stated unconditionally when the standard makes it conditional on manual review; a false-positive-reduction figure attributed to a code-review benchmark that does not contain it; METR’s confidence interval given as +2% to +38% when it is +2% to +39%, with the wrong claim about where it appears; requirement 12.10.7 applied to transmission when it governs discovery of stored data; a Veracode caveat asserting per-category figures were not restated when they were; and two executive quotations attached to a paper that does not contain them. Four of the six were attribution errors rather than wrong facts — the number was right, the source was not. That is the failure mode worth internalising from this exercise.

One live shift worth watching rather than acting on yet: in Aug 2026 both Willison and Osmani argued that line-by-line review does not scale past a few parallel agents and that other verification strategies matter more. That does not relax accountability at the merge boundary — someone other than the author still owns the outcome — but it does mean "read every line" is now a contested mechanism rather than a consensus one.

Known gaps, stated plainly

No 2026 DORA State of DevOps survey exists yet. The 2026 DORA artifact is an ROI modelling framework, and its headline figures are outputs of an illustrative 500-person scenario — not measured findings. Don't cite them as evidence.

PCI SSC has published no standard specific to coding agents. It has published AI Principles for payment environments and guidance for assessors using AI. Existing PCI DSS requirements apply unchanged. Anyone claiming there is an "AI requirement" is wrong — and requirement numbers in any policy document must be verified against the official standard, not against secondary summaries including this one.

Nothing rigorous exists yet on fully multi-agent SDLC workflows (agent writes → agent reviews → agent deploys). The closest evidence — serial task completion collapsing to 20% across a pipeline — argues for caution, not enthusiasm.

Why this exists

The question behind it: how does anyone actually know they are using AI well, rather than just using it a lot? Long practice is not evidence of good practice. Nobody in the room had an answer worth trusting, so this started as a test of my own habits — every claim traced back to a primary source and checked against how I was actually working.

Several of my habits did not survive that. The corrections are in here, and they changed how I work day to day. That is the standard the document has to meet: a guide worth following has to be able to tell its own author he was wrong. Beyond that, it exists so an organization adopting AI is supercharged by it rather than bogged down by it, and so that anyone citing a practice from it can defend where the practice came from.

Keep this current

Capability doubles roughly every four months, so treat this document the way you'd treat a dependency: review it quarterly, date-stamp what changes, and delete what's been superseded. When a practice here stops matching reality, the fix is a pull request, not a workaround.
